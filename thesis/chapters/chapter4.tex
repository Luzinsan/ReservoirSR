\chapter{Implementation}
\label{chap:implementation}

The methodology of Chapter~\ref{chap:methodology} is realized as a complete software complex that covers the full lifecycle of a reservoir super-resolution surrogate, from the generation of paired coarse-grid and fine-grid datasets to interactive inference within a desktop application. This chapter documents the implementation: the overall software architecture, the construction of the dataset, the neural network configurations, the training infrastructure, the export of the deployed model, and the interactive application that exposes the surrogate to the end user. The chapter follows the same logical order as Chapter~\ref{chap:methodology} and reports the specific numerical values, software components, and configuration parameters that were deliberately omitted from the methodological discussion.

\section{Implementation Overview}
\label{sec:implementation_overview}

The software complex is structured as four loosely coupled subsystems that communicate through well-defined data formats rather than through shared in-memory state. The numerical simulator is implemented as a standalone service that produces paired reservoir solutions on demand. The training infrastructure consumes these solutions, fits the normalization statistics, trains the neural surrogates, and emits portable model artefacts. The export tool converts the trained checkpoints into a portable inference format that no longer depends on the training framework. The interactive desktop application loads the exported artefacts and orchestrates evaluation, comparison, and live inference. The relationships between the four subsystems and the data formats that connect them are summarized in Figure~\ref{fig:impl_architecture}.

The training infrastructure relies on PyTorch~2.x as the deep learning framework, PyTorch Lightning as the training engine, Hydra for hierarchical configuration management, and MLflow for experiment tracking. The export tool relies on ONNX as the portable model format and ONNX~Runtime as the inference engine, with the latter also embedded in the desktop application. The simulator service exposes a gRPC interface based on protocol buffers, which allows the same service to be consumed both by the dataset generation pipeline and by the desktop application for live simulation. The desktop application is implemented in PySide6 and follows an observer-based reactive architecture that is described in Section~\ref{sec:impl_gui}.

Configuration of all training and export experiments is centralized in a Hydra configuration tree, with composable sub-groups for data, models, optimizers, schedulers, losses, and trainer settings. Each experiment described in Chapter~\ref{chap:methodology} corresponds to a named configuration file that overrides the relevant defaults and is reproducible by a single command. The artefacts produced by every run, including checkpoints, normalization statistics, MLflow records, and a CSV report with the final KPI metrics, are written to a configurable artefacts directory.

\section{Numerical Simulator and Dataset Construction}
\label{sec:impl_dataset}

The dataset is constructed by repeatedly invoking a numerical simulator over a sampled population of reservoir scenarios. The simulator itself is a separate component of the system, accessed through a gRPC service that exposes operations to initialize a simulation, run a configurable number of time steps, retrieve the current spatial fields, and run a full snapshot-stride job in the background. The gRPC interface allows the same simulator to be consumed by the offline dataset generation pipeline and by the interactive desktop application for live simulation in parallel with neural surrogate inference.

The reservoir model is parameterized by a structured configuration that combines fluid properties (densities, viscosities, gas content), geometric properties (well radius, contour radius, layer thicknesses), well operations (bottom-hole pressure, water cut limits, operational regime), temporal configuration (time-step length, total simulation horizon, snapshot stride), solver tolerances (pressure and saturation convergence thresholds in both fracture and matrix systems), and per-layer petrophysical parameters (porosities, saturation bounds, permeabilities, layer flags). Five layers are used in all scenarios.

The dataset generation pipeline is driven by a campaign engine that samples scenarios from this parameter space using Latin Hypercube Sampling. Twenty-nine parameters are subject to sampling. Twenty-one of them follow the linear scale: well operations such as bottom-hole pressure on the interval from 15 to 70~bar, contour water cut limit from 80 to 360~bar, total flow rate from 120 to 480~$\text{m}^3/\text{d}$, contour pressure from 90 to 210~bar; reservoir geometry such as the well radius from 0.05 to 0.35~m and the contour radius from 3 to 12~m; fluid rheology such as the non-Newtonian breakdown viscosity from 4 to 18~cP and the saturation-shift parameters on the unit interval; and four saturation shift parameters that perturb the irreducible and maximum saturations of each layer by at most $\pm 0.15$ within the physical bounds. Eight parameters that vary over several orders of magnitude are sampled on a logarithmic scale: the absolute permeabilities of all five matrix and fracture layers in the range from $10$ to $1000$~mD, and the four solver tolerances (pressure and saturation convergence thresholds in matrix and fracture systems) in the range from $10^{-7}$ to $10^{-3}$.

Each sampled scenario is validated before being submitted to the simulator. The validity checks reject scenarios in which the requested simulation horizon is shorter than the number of snapshot steps multiplied by the time-step length, in which the total flow rate falls below a quarter of the bottom-hole flow rate (a physical lower bound on the production-injection balance), in which the irreducible saturation exceeds the maximum saturation in any layer, in which the well coordinates coincide, or in which any solver tolerance, time step, or sub-stepping factor is non-positive. Scenarios that fail any of these checks are discarded and replaced by the next sample from the campaign iterator. The acceptance rate of the sampler on the parameter ranges adopted in this work is approximately 78\%; the corresponding sampled and rejected counts are recorded as part of the dataset metadata to characterize the effective acceptance rate of the sampler.

For every accepted scenario, the simulator runs two independent jobs. The first job uses the coarse-grid configuration with 25 cells along the horizontal axis. The second job uses the fine-grid configuration with 100 cells along the same axis, while the layer-wise vertical discretization is preserved. Both jobs share the time-step length, the snapshot stride, and all physical parameters; they differ only in the lateral grid resolution. The fixed upscaling factor of four between the two grids is therefore consistent across the dataset. Each job produces fifty sequential snapshots at uniform intervals of simulation time, and each snapshot contains the pressure field and the two saturation channels evaluated on the corresponding grid.

Snapshots are serialized into a custom archive format. Each archive is a ZIP container that combines a JSON metadata document with several NumPy arrays stored in the standard \texttt{.npy} format. The metadata document records the names of the channels, the names of the dynamic, static, and layer scalars, and references to the source simulation runs. The arrays carry the low-resolution and high-resolution field tensors of shape $(T, C, H, W)$, the dynamic scalars of shape $(T, F_{\text{dyn}})$, the static scalars of shape $(F_{\text{stat}})$, and the layer scalars of shape $(L, F_{\text{layer}})$. The format avoids the use of pickle and is therefore safe to load in untrusted environments. The archive layer is implemented as a small class with explicit read and write entry points, so that the same code path is used by the dataset generation pipeline, the training infrastructure, and the interactive application. The campaign producing the experiments reported in Chapter~\ref{chap:results} contains 500 accepted scenarios, yielding twenty-five thousand snapshot pairs in total.

The campaign engine itself supports parallel execution of multiple simulator jobs through a job queue with a configurable worker limit, with periodic polling of the gRPC service for completion. Jobs that fail or are cancelled by the user are recorded but do not interrupt the campaign. A campaign can be paused and resumed, which is essential for runs that span several hours of simulator wall-clock time.

\section{Neural Architectures}
\label{sec:impl_models}

The neural surrogate is implemented as a family of PyTorch modules, all of which accept a batch dictionary as input and return a tensor of high-resolution fields. The dictionary always carries the low-resolution input tensor under a fixed key, and optionally carries a conditioning vector for the FiLM-conditioned MDSR variant. This uniform interface allows the same training loop, evaluation code, and export pipeline to be used for every architecture.

\subsection*{Regression backbones}

The MSRResNet generator is a moderate-depth residual model with eight residual blocks. Each residual block consists of two $3 \times 3$ convolutions with a ReLU non-linearity between them, followed by a residual scaling factor of $0.1$. The network uses sixty-four feature channels throughout the trunk. Upsampling by the fixed factor of four is performed at the tail through two cascaded sub-pixel upsamplers of factor two each, in the manner of Shi et al.~\cite{shi2016real}. The number of trainable parameters is approximately $4.5 \times 10^{5}$.

The MDSR generator follows the same overall structure but uses sixteen residual blocks and supports optional FiLM modulation. In the unconditional variant, the conditioning dimension is zero, no auxiliary encoder is instantiated, and the network reduces to a deeper variant of MSRResNet with sixteen residual blocks. In the conditioned variant, an auxiliary encoder maps the conditioning vector into an embedding of dimension $256$, a FiLM generator produces per-block scale and shift parameters for the residual trunk, and the FiLM layers are initialized to the identity transformation as required by the methodology of Section~\ref{sec:methodology_conditioning}. The unconditional MDSR has approximately $8.5 \times 10^{5}$ parameters; the conditioned variant adds the parameters of the encoder and the FiLM generator, which depend on the dimension of the conditioning vector.

The RFDN generator follows the residual feature distillation paradigm of Liu et al.~\cite{liu2020rfdn}, with six distillation blocks operating on fifty feature channels. Each block combines four shallow distillation paths through a $1 \times 1$ convolution and applies an enhanced spatial attention module on the aggregated features. The total number of trainable parameters is approximately $5.5 \times 10^{5}$, comparable to MSRResNet but with a markedly different distribution of capacity across depth.

\subsection*{Conditioning encoder}

When FiLM conditioning is enabled, the conditioning vector enters the network through a two-layer encoder with $256$ hidden units and a ReLU non-linearity. A subsequent linear projection produces $2 \cdot N_{\text{blocks}} \cdot N_{\text{features}}$ values, organized as a scale and a shift parameter for each residual block of the trunk. The output projection is initialized with zero weights and with biases that produce a unit scale and a zero shift, so that the FiLM modulation acts as the identity at the beginning of training. This identity initialization is the precondition for the controlled comparison described in Section~\ref{sec:methodology_conditioning}.

The composition of the conditioning vector is controlled by a Hydra sub-configuration. Three named configurations are used. The \texttt{none} configuration disables conditioning entirely and reduces the conditioning dimension to zero. The \texttt{minimal} configuration includes only the simulation time and the bottom-hole pressure, yielding a two-dimensional conditioning vector. The \texttt{full} configuration includes all dynamic scalars (fourteen values), all static scalars (fifty-seven values), and all layer scalars (sixty values, organized as twelve features tiled across the five layers), yielding a conditioning vector of dimension $131$. A fourth named configuration \texttt{dynamic\_only}, which includes all fourteen dynamic scalars but disables the static and layer scalars, is defined in the configuration tree but is not exercised by the experiments reported in the present work.

\subsection*{Discriminator}

The discriminator used in all adversarial experiments is a residual PatchGAN whose input is the residual between the candidate high-resolution field and a bicubic upsampling of the low-resolution input. This residual formulation focuses the discriminator on the high-frequency content invented by the generator rather than on the low-frequency content shared with the bicubic baseline. The network is composed of strided convolutions with spectral normalization on every layer and LeakyReLU activations with negative slope $0.2$. The number of channels doubles at each downsampling stage from sixty-four to at most five hundred and twelve. The final layer is a $1 \times 1$ convolution that produces a patch-level decision map. Spectral normalization caps the Lipschitz constant of each layer and stabilizes adversarial training in line with the recommendations of the broader literature.

The discriminator forward pass is performed in single-precision floating-point even when the rest of the training loop uses mixed-precision arithmetic; spectral normalization is sensitive to reduced precision, and this configuration prevents instabilities observed during early experiments.

\subsection*{Physics-aware perceptual modules}

The perceptual criterion of Section~\ref{sec:methodology_adversarial} is implemented as a dedicated module that bundles the gradient and spectral penalties. The gradient component convolves each channel with the orthogonal Sobel kernels and applies an $L_1$ penalty to the difference between predicted and reference gradient components, using depthwise convolutions to keep the channels independent. The spectral component takes the two-dimensional real-input Fast Fourier Transform of both fields in single-precision floating-point, applies an $L_1$ penalty to the difference between the amplitude spectra, and uses the orthogonal normalization convention so that the penalty is invariant to the spatial dimensions of the input. The two components are combined with configurable weights that default to one for the gradient component and one half for the spectral component.

The physics-informed regularization of Section~\ref{subsec:physics_reg} is implemented as a second dedicated module. The pressure smoothness term applies the standard five-point discrete Laplacian to the pressure channel and reports the mean absolute value of the result. The front consistency term computes the gradient magnitude of each saturation channel using the same Sobel convolutions as the perceptual module, with a small constant added under the square root for numerical stability, and applies an $L_1$ penalty to the difference between predicted and reference magnitudes. The two terms are combined with configurable weights that default to $0.2$ for the pressure smoothness component and $1.5$ for the front consistency component.

\section{Training Infrastructure}
\label{sec:impl_training}

The training pipeline is built around PyTorch Lightning and uses Hydra to compose hierarchical configurations of the data module, the model, the trainer, and the experiment-specific overrides. Two Lightning modules are implemented: a regression module for the pixel-loss baselines and the conditioning experiment, and an adversarial module for the GAN experiments. Both modules share the same data interface and the same metric collection.

The regression module wraps the chosen backbone, the pixel-loss function (Charbonnier loss with $\varepsilon = 10^{-3}$ for the pixel-only baselines), and a collection of validation metrics: PSNR and absolute error per channel and on average, SSIM, ERGAS, SAM, and the gradient-based front consistency metric. The AdamW optimizer with decoupled weight decay is used with a learning rate of $4 \times 10^{-4}$ for the MSRResNet and RFDN baselines, $5 \times 10^{-4}$ for the unconditional MDSR baseline, and $2 \times 10^{-4}$ for the conditioned MDSR variants. The weight decay is set to $10^{-4}$. A cosine annealing schedule decays the learning rate to $10^{-6}$ over the full training horizon. The training horizon is one hundred and fifty epochs for the regression baselines and one hundred epochs for the conditioned MDSR. Gradient clipping with a maximum norm of five is applied throughout. An exponential moving average of the generator weights is maintained with decay $0.999$, and validation metrics are computed on the moving-average parameters rather than on the live model.

The adversarial module implements the three-phase schedule of Section~\ref{sec:methodology_adversarial}. The discriminator warm-up phase lasts five epochs, during which only the discriminator is updated. The generator warm-up phase lasts an additional five epochs, during which the generator is refined under the pixel, perceptual, and physics-informed objectives but not under the adversarial signal. The full objective is activated after epoch ten. Manual optimization is used throughout, with separate Adam optimizers for the generator and the discriminator: a learning rate of $5 \times 10^{-5}$ for the generator and $2 \times 10^{-4}$ for the discriminator, both with $\beta_1 = 0.9$ and $\beta_2 = 0.99$. Cosine annealing schedules apply to both. The adversarial training horizon is one hundred epochs for the MSRResNet-based experiment and one hundred and fifty epochs for the MDSR and RFDN variants. Gradient clipping with a maximum norm of one is applied throughout the adversarial experiments, which is markedly tighter than the value used in the regression baselines and reflects the higher gradient variance characteristic of adversarial dynamics. The adversarial loss weight is $3 \times 10^{-2}$ for the MSRResNet-based experiment, in which the adversarial signal acts on top of the full physics-aware objective, and $10^{-1}$ for the MDSR and RFDN variants, in which the physics-informed regularizer is not applied. The pixel weight, the perceptual weight, and the physics-informed weight in the MSRResNet-based configuration are $2.0$, $0.5$, and $0.3$ respectively.

Three stabilization techniques are applied in addition to the staged schedule. First, a relativistic average formulation of the discriminator objective is used, in which each input is judged not in absolute terms but relative to the average score of the batch. Second, the discriminator update is skipped on any iteration in which its loss falls below $0.35$, which prevents the discriminator from overpowering the generator; this skip can be temporarily disabled every five epochs to allow the discriminator to recover after generator improvements. Third, Gaussian noise with standard deviation $0.02$ is injected into the discriminator input and decayed linearly to zero over thirty epochs, which smooths the decision boundary in the early phases of training when the generator is still close to its pixel-loss state. The exponential moving average of the generator is maintained with decay $0.995$ for the MSRResNet-based experiment and $0.99$ for the other variants.

Every adversarial experiment is initialized from a pre-trained pixel-loss checkpoint of the same backbone, in line with the pre-training pipeline of Section~\ref{sec:methodology_comparative}. The checkpoint is loaded from disk before training begins, the missing or unexpected keys are reported but not fatal, and the moving-average buffer is initialized from the same checkpoint to avoid producing zero outputs at the first validation step.

\subsection*{Data module and normalization}

The data module is responsible for discovering archive files in a configured directory, splitting them into training, validation, and test partitions at the scenario level using a fixed seed of forty-two, fitting the normalization statistics on the training partition before the first epoch, and constructing PyTorch data loaders that emit batched tensor dictionaries. The split fractions are $70\%$ for training, $15\%$ for validation, and $15\%$ for testing.

Normalization is implemented as a separate module that consumes a JSON statistics file produced once per dataset. For each parameter group, a strategy is selected from one of \texttt{minmax}, \texttt{zscore}, \texttt{log\_minmax}, \texttt{log\_zscore}, or \texttt{none}. The default configuration applies \texttt{zscore} to the pressure channel, \texttt{minmax} to the saturation channels, \texttt{log\_minmax} to the permeabilities, \texttt{minmax} to most well and reservoir scalars, \texttt{zscore} to the dissipation scalars, and \texttt{none} to flag and grid parameters. Logarithmic strategies are masked out whenever the underlying parameter contains non-positive values, with a fall-back to the corresponding linear strategy. Statistics are pre-computed as broadcast-ready arrays at initialization, so that the normalization step inside the data loader reduces to a single multiplication and addition.

The training data loader uses a batch size of one hundred and twenty-eight, ten worker processes with persistent worker mode enabled, and pinned memory. Each worker maintains its own LRU cache of up to one hundred and twenty-eight loaded archives to keep frequently accessed scenarios resident in memory across epochs.

\subsection*{Logging, checkpointing, and reproducibility}

The Lightning trainer runs on a single NVIDIA H100 GPU in bfloat16 mixed-precision arithmetic, with cuDNN benchmarking enabled. Training metrics are logged every twenty optimizer steps; validation is performed every two epochs for the adversarial experiments and every five epochs for the regression baselines, to balance feedback frequency against the cost of the heavier metrics. MLflow records the full set of metrics, the resolved configuration tree, and the rendered field visualizations of every training run. Standard Lightning checkpointing retains the best model on validation loss together with the last model of every epoch.

A dedicated visualization callback is registered for every training run. The callback selects a fixed subset of validation archives at the first epoch, retains the same subset across all subsequent epochs, and renders four panels per channel at every validation step: the low-resolution input, the high-resolution reference, the network output, and the absolute difference. The fixed-subset selection is essential for diachronic comparison: the user inspects the same scenarios across epochs and observes the qualitative evolution of the surrogate rather than a different scenario at every epoch. Rendered figures are dispatched to either TensorBoard or MLflow depending on the logger active for the run.

A second callback records the final KPI metrics of every run into a shared CSV report. The report retains the best validation score of every monitored metric, the corresponding epoch, and a pass-or-fail flag against pre-declared thresholds: PSNR above $30$~dB, SSIM above $0.88$, ERGAS below $6.0$, gradient mean absolute error below $0.030$, and maximum absolute error below $0.200$. The report grows monotonically across experiments, which allows direct comparison of all runs reported in Chapter~\ref{chap:results} from a single artefact.

Reproducibility is enforced by the combination of three mechanisms. Random number generators of PyTorch, NumPy, and the Python standard library are seeded at the value declared in the global configuration. The data split is computed deterministically from the same seed, so that the same scenarios appear in the same partition across runs. Normalization statistics are persisted to disk after the first run on a given dataset and loaded verbatim by every subsequent run on the same data, which guarantees that the input distribution of the network is identical across experiments.

\section{Export and Inference Pipeline}
\label{sec:impl_export}

A trained Lightning checkpoint is not directly usable in a desktop application: it carries the full optimizer state, the training-time data loaders, and the PyTorch Lightning runtime, none of which are appropriate for interactive deployment. The export pipeline converts a checkpoint into a portable ONNX graph that depends only on ONNX~Runtime at inference time.

The export tool first extracts the relevant weights from the checkpoint. By default, it prefers the exponential moving average weights of the generator if they are present, and falls back to the live weights otherwise. Architectural hyperparameters such as the number of residual blocks and the feature width are read from the saved hyperparameters of the checkpoint and used to instantiate a fresh generator with the matching topology, which protects the export against configuration drift between training and deployment. The generator is then wrapped in a thin module that accepts a positional tensor instead of a batch dictionary, so that the exported graph has a single named input and a single named output.

The wrapped module is traced through the standard ONNX exporter with opset version seventeen, with constant folding enabled, and with dynamic axes declared for batch and spatial dimensions on both input and output. The resulting ONNX file therefore supports any batch size and any spatial resolution at inference time, subject to the upscaling factor of four.

A verification step is performed on every export. A deterministic dummy input is generated, the predictions of the PyTorch wrapper and of the ONNX~Runtime session are compared element-wise, and the export is rejected if the maximum absolute difference exceeds $10^{-3}$. This check protects against silent regressions caused by unsupported operators or by precision mismatches in the ONNX graph. The export tool supports two modes: a single-checkpoint mode that converts one specific checkpoint into one ONNX file, and a batch mode that converts every checkpoint in a directory and writes a per-file report of successes and failures.

At inference time, the deployed surrogate is consumed through a dedicated inference engine. The engine loads the ONNX session with all graph optimizations enabled and exposes a small interface for upscaling a single coarse-grid tensor and for upscaling a batch of tensors with pre-fetching. The inference engine maintains an internal FIFO cache of recently upscaled frames indexed by the timestep identifier, with a fixed capacity of one thousand and twenty-four entries; this cache supports interactive slider scrolling in the evaluation panel of the desktop application without re-running the network for previously visited timesteps. The same normalization module used at training time is shared between training and inference: the JSON statistics file is loaded from disk before the first inference call, the low-resolution input is normalized with the training-time low-resolution statistics, and the network output is denormalized with the training-time high-resolution statistics. This shared normalization pipeline removes a common source of train-test mismatch.

\section{Interactive Surrogate Application}
\label{sec:impl_gui}

The interactive desktop application exposes the trained surrogate to engineers who do not need to run a training loop. The application is implemented in PySide6 and follows an observer-based reactive architecture in which user interface widgets are bound to typed data models, and changes in the data models are propagated to the widgets through a small custom reactive layer.

The overall component layout is summarized in Figure~\ref{fig:gui_architecture}. The application root holds a single application context that aggregates the navigation state, three configuration sub-objects (general, data, inference), and a logging bus through which every module emits structured events. All configuration sub-objects derive from a shared observable model base class that intercepts attribute assignments on dataclass-declared fields and notifies registered listeners. A widget that needs to reflect a configuration value subscribes to the corresponding field at startup and receives a notification whenever the value changes, regardless of whether the change originates from the user interface, from the settings dialog, or from a configuration reload.

Configuration of the application is loaded from a Hydra configuration directory at startup, with the same composition mechanism used for training: a default file references three sub-configurations (general, data, inference), each of which carries a Hydra package directive that places its keys at the expected location in the configuration tree. When the user edits settings through the settings dialog, the changes are written back to the same configuration files, so that the next start of the application observes the updated state. The settings dialog operates on a snapshot of the live context and commits the snapshot atomically on acceptance, which prevents partially applied changes if the user cancels the operation mid-way.

\subsection*{Feature modules}

Three feature modules are implemented, each bound to a tab of the main window through a declarative specification that maps model fields to widget identifiers and binding kinds. The data module supports offline dataset inspection and live simulation. The evaluation module compares the neural surrogate, classical interpolation, and the high-resolution reference on test scenarios. The log panel renders structured events emitted by every module.

The data module exposes three operating modes through a tab widget. The runtime mode connects to the gRPC simulator, initializes a simulation from the current configuration, and advances the simulation by one or several time steps per playback tick. The generation mode submits campaign jobs to the simulator and polls them for progress. The dataset-view mode opens a previously generated archive and replays its snapshots through the playback timeline. The three modes share a single playback controller that owns one timer and dispatches tick events to whichever mode is currently active. Mode switching is disabled during playback to prevent races on the underlying gRPC channel or archive handle.

The rendering controller of the data module supports three render strategies. The deterministic strategy applies vectorized bilinear interpolation over each grid cell and serves as the cheap visual baseline. The smoothing strategy applies a higher-resolution interpolation pass for visualization purposes only. The neural strategy invokes the embedded inference engine on the current snapshot and returns a neural super-resolution reconstruction at the deployed scale. A combo box on the data tab lets the user switch between the three strategies in real time, and the cached frames of the inference engine ensure that switching back to a previously visited snapshot does not trigger a new network evaluation.

The evaluation module loads an exported ONNX surrogate together with a dataset partition and reproduces, in the application, the same scenario-level split used at training time. The same random seed of forty-two and the same train, validation, and test fractions of $70\%$, $15\%$, and $15\%$ are used, which guarantees that the partition exposed in the application coincides with the partition reported in Chapter~\ref{chap:results}. The evaluation module displays the low-resolution input, the fine-grid reference, the neural prediction, and the absolute-difference map on a three-by-four grid of plots, with shared colour scales per channel. A prefetch operation upscales sixteen frames at a time and pushes them into the engine cache, which allows the user to scrub through the full simulation history of a scenario at interactive rates.

\subsection*{Rendering pipeline}

Field visualizations are produced through a dedicated rendering pipeline built on top of \texttt{pyqtgraph}. Each plot maintains a single image item that is created once and updated in place at every refresh; image items are never destroyed and re-created. Channel-specific lookup tables are pre-computed at startup and assigned once to each image item; subsequent refreshes pass only the new array and the per-frame value range. Isoline overlays are drawn as separate items above the image with their colour taken from the same palette as the image, so that the isolines remain visually consistent with the field. The deterministic bilinear baseline is implemented in fully vectorized NumPy through broadcasting over a small sub-pixel grid, which renders it at the same display resolution as the neural surrogate without an iterative loop in Python.

The metric panel of the application is rendered through the plotting infrastructure of \texttt{pyqtgraph} rather than through Matplotlib, which avoids the cost of repeatedly redrawing entire figures and keeps the interface responsive during live simulation. Metric snapshots emitted by every simulation step are aggregated in a lightweight observable container that is shared between the simulation controller and the metric panel, so that the latter updates incrementally rather than re-reading the entire history at every step.

\subsection*{Logging subsystem and infrastructure}

A structured logging subsystem connects every module to a single log panel embedded in the main window. Loggers are organized as a hierarchy in which child loggers prepend a scope name to every event and forward the resulting structured record to a shared log bus. The bus emits a Qt signal carrying a rendered HTML representation of the record; the log panel is implemented as a \texttt{QWebEngineView} that appends incoming HTML through a small JavaScript bridge. The choice of \texttt{QWebEngineView} over \texttt{QTextEdit} is motivated by the need to support collapsible JSON payloads through \texttt{<details>} and \texttt{<summary>} elements, which is not supported by \texttt{QTextEdit}. A pending queue absorbs records emitted before the embedded browser is ready, and a hard cap of three thousand visible records prevents unbounded memory growth during long sessions. Loggers respect the global log level declared in the general configuration and filter incoming records before producing any HTML.

Communication with the simulator service is encapsulated in a single gRPC client that exposes the operations required by the data and evaluation modules: starting and stepping a simulation, fetching the current spatial fields, dispatching a dataset job, querying the job status, and closing the underlying channel on application shutdown. The protobuf stubs are generated once from the service definition and loaded lazily on the first call, so that an application started in offline mode never pays the cost of importing the generated stubs.
